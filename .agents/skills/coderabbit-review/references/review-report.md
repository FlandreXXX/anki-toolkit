# Накопительный отчёт CodeRabbit: формат, история, публикация

Этот файл — **единственный владелец** формата накопительного отчёта, его истории и
специализированной публикации. Общую процедуру Git/GitHub (ветка, индекс, commit,
push, проверка удалённого SHA, создание и изменение PR, Draft/Ready, merge) владеет
[`../../git-workflow/SKILL.md`](../../git-workflow/SKILL.md): здесь только то, что
относится к отчёту CodeRabbit.

Отчёт живёт в **одном** top-level issue-комментарии автора PR во вкладке
Conversation — не в inline review thread, не в сообщении бота и не в описании PR.

## 1. Формат

Точный служебный маркер отдельной строкой и одна видимая связная таблица GFM:

```markdown
<!-- coderabbit-disposition -->

| Итерация / reviewed HEAD | Уровень | Путь | Влияние | Решение | Исправление |
| --- | --- | --- | --- | --- | --- |
| 1 · `0123456` | major | `path/to/file.go` | Потеря данных при отмене | confirmed | Исправлено в `abcdef0` |
```

Правила формата:

- маркер `<!-- coderabbit-disposition -->` встречается ровно один раз, занимает
  отдельную строку и виден: маркер внутри HTML-комментария, ограждённого блока,
  блока кода с отступом, цитаты или raw HTML не засчитывается;
- одна видимая таблица: точный заголовок из шести столбцов, сразу за ним строка
  разделителя из шести ячеек дефисов (выравнивание `:` допустимо), затем хотя бы
  одна строка данных подряд, без разрыва, второго заголовка и оторванных строк;
- шесть непустых ячеек в каждой строке; минимальной длины ячейки нет;
- внутренняя `|` экранируется по GFM (`\|`) — в том числе внутри code span,
  поскольку GFM режет таблицу раньше, чем распознаёт строчный код; чётность
  обратных слэшей имеет значение. Одна физическая строка на строку таблицы;
- заголовок `## …` над таблицей не требуется и не проверяется; обычная проза
  вокруг таблицы допустима, включая одиночный `|` в тексте после неё.

## 2. Ячейки

- **Итерация / reviewed HEAD** — положительный номер итерации, `·` и reviewed HEAD
  в code span: от 7 до 40 строчных шестнадцатеричных символов. Предпочитай полный
  установленный SHA; сокращение — только при доказанной уникальности. Номера
  последовательны (1…N без пропусков), строки одной итерации идут подряд и имеют
  один и тот же reviewed SHA.
- **Уровень** — фактическая severity провайдера без переименования (`critical`,
  `major`, `minor`, `trivial`, `info`, `none`).
- **Путь** — затронутый файл.
- **Влияние** — технический эффект замечания, одна строка.
- **Решение** — каноническое: `confirmed`, `partially confirmed`, `false positive`,
  `stale`, `duplicate`, `out of scope`, `unconfirmed`, `clean`.
- **Исправление** — что фактически сделано и каким коммитом опубликовано, либо
  обоснованный отказ. Фиктивные fix SHA не пишутся; коммит исправления не
  смешивается с reviewed HEAD той же итерации.

Не копируй в таблицу сырой вывод CLI, промпты, длинные `codegenInstructions`,
инструкции ревьюера как распоряжения, секреты и логи.

## 3. Итерация без findings

Только при нуле findings итерация закрывается **одной** строкой `clean`: `—` в
столбцах «Уровень» и «Путь», `clean` в «Решение», опубликованный маркерный коммит
в «Исправление». Совмещение `clean` и строк-findings одной итерации, как и `—` в
уровне или пути не-clean строки, — нарушение контракта.

При ненулевых findings сохраняются все решения, даже если правок не потребовалось:
`false positive`, `stale`, `duplicate` и `out of scope` не выдаются за выполненное
исправление.

## 4. История

- История дополняется: прежние строки не удаляются и не переписываются ради
  красивого итога.
- Исправление ошибки в исторической строке — только явно согласованное действие.
- Лимит 10 000 кодовых точек относится к описанию PR, а не к комментарию.
- Если отчёт перестаёт помещаться в допустимый размер комментария — остановись,
  не заводи второй журнал и не урезай историю; сообщи о препятствии.
- Существующая неожиданная история не уничтожается: этот проект не требует
  автоматической миграции старых таблиц из описания PR.

## 5. Публикация

1. Установи PR, repo, base, head и **фактический numeric ID автора** через API;
   проверь, что активная учётная запись может писать от этого автора. Не выдавай
   свой комментарий за комментарий другого автора.
2. Прочитай **полную** пагинированную выдачу Conversation. Ищи точный текст
   маркера, даже если он размещён неправильно; проверяй ID, принадлежность к PR и
   авторство по API. Ноль кандидатов допускает создание только после
   действительно выполненного ревью; один подходящий — обновление по его ID;
   чужой маркер, несколько кандидатов или неполная выдача — остановка без
   удаления и без выбора произвольного комментария.
3. Восстанови полный опубликованный текст и прежние строки, сверь с локальной
   рабочей копией и примири расхождения. Прогони локальную проверку (§ 6),
   сверь данные с фактическим результатом ревью, перечитай комментарий
   непосредственно перед записью. При неизвестных изменениях остановись.
4. Пиши штатным `gh api` или доступным GitHub-инструментом, передавая тело как
   **данные из файла**: для `gh api` используй `--input` с JSON-файлом, потому что
   `-f body=@file` подставляет строку `@file` буквально, а не читает файл.
5. После записи прочитай комментарий по ID и всю выдачу заново: сравни
   содержимое, единственность, автора, принадлежность к PR, head/base и состояние
   PR; проверь прочитанный текст той же проверкой. Старые строки неизменны, новые
   добавлены ровно один раз.
6. Не повторяй сетевую мутацию при неизвестном исходе, не прочитав удалённое
   состояние. Повторное чтение не является атомарной блокировкой: при расхождении
   итерация не завершена.

`git-workflow` остаётся владельцем общей публикации: его справочники не
дублируют этот контракт, а ссылаются на него.

## 6. Проверка

Локальная проверка формы отчёта (маркер и таблица на подготовленном тексте):

```bash
go run .github/scripts/coderabbit-comment-lint/main.go --comment-file "$comment_file"
```

Сетевая read-only сверка опубликованного состояния (идентичность PR, автор,
полная выдача комментариев, повторное чтение PR):

```bash
go run .github/scripts/coderabbit-comment-lint/main.go --event-file "$GITHUB_EVENT_PATH"
```

Сетевой режим требует `GITHUB_REPOSITORY` и `GITHUB_TOKEN` в окружении шага, не
делает ничего кроме GET к `https://api.github.com` и не проверяет структуру
описания PR — это отдельная проверка. Отсутствие отчёта допустимо только после
полного достоверного чтения; отсутствие отчёта не доказывает, что ревью
проводилось.

### Локальный запуск сетевой сверки

`GITHUB_EVENT_PATH` существует только на runner'е GitHub Actions. Локальная
оболочка цикла его не получает, поэтому для локальной сверки файл события
создаётся из фактического состояния PR, а не выдумывается:

```bash
gh pr view <number> --json number,headRefOid,headRepositoryOwner,headRepository > /tmp/pr.json
python3 - /tmp/pr.json <<'PY' > /tmp/event.json
import json, sys
pr = json.load(open(sys.argv[1], encoding="utf-8"))
json.dump({
    "repository": {"full_name": pr["headRepositoryOwner"]["login"] + "/" + pr["headRepository"]["name"]},
    "pull_request": {"number": pr["number"], "head": {"sha": pr["headRefOid"]}},
}, sys.stdout)
PY
GITHUB_REPOSITORY=<owner>/<repo> GITHUB_TOKEN=$(gh auth token) \
  go run .github/scripts/coderabbit-comment-lint/main.go --event-file /tmp/event.json
```

Минимальный проверяемый снимок события — `repository.full_name`,
`pull_request.number` и полный `pull_request.head.sha`: линтер сверит их с
ответом API и откажет, если HEAD PR успел измениться. Токен передаётся только в
окружение команды; в файл события и в аргументы командной строки он не попадает.
Неверные `GITHUB_REPOSITORY`, `GITHUB_TOKEN` или несуществующий SHA дают exit `2`
или отказ сверки, а не ложный успех.

Линтер проверяет форму, историю и авторство; он **не** доказывает, что ревью
действительно было, что findings приведены полно и что коммиты существуют.
