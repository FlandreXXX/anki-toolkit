# Переиспользование и зависимости

Используй этот референс, когда выбираешь между уже имеющимся кодом, средствами Go, текущими зависимостями, новой библиотекой и собственной реализацией. Сверяй поведение с нужным контрактом и версиями, которые реально использует проект.

## Найди владельца действующего контракта

- До написания нового механизма найди определения, вызывающий код, тесты, внешние форматы и правила проекта. Уточни, кто владеет поведением и какие потребители от него зависят.
- Переиспользуй существующую функцию или тип, если совпадает семантика, включая обработку ошибок и крайних случаев. Расширяй канонического владельца правила, если именно он должен отвечать за новое поведение.
- Не объединяй внешне похожие правила с разными контрактами только ради уменьшения строк или числа функций. Сохраняй отдельные реализации, пока их смысл действительно различается.
- Если общий механизм не поддерживает требуемый случай, исправляй или расширяй его на правильной границе. Не добавляй параллельную реализацию, локальный обход или специальные условия для одного примера.

## Выбери библиотеку по требуемому поведению

Сначала проверь документацию и исходники той версии Go или пакета, которая доступна проекту. Название библиотеки не подтверждает, что она сохраняет нужные данные, принимает нужную грамматику или обеспечивает необходимые гарантии.

| Задача | С чего начать | Когда рассматривать другой вариант |
| --- | --- | --- |
| Обычный JSON | Для нового применения рассматривай стабильный [`encoding/json/v2`](https://pkg.go.dev/encoding/json/v2). Документация [`encoding/json`](https://pkg.go.dev/encoding/json) рекомендует его, если он доступен в минимальной поддерживаемой версии Go и семантика соответствует контракту. | Сохраняй v1, если этого требует существующий контракт или совместимость. v1 остаётся поддерживаемым, автоматическая миграция не обязательна. Проверь различия `null`, nil- и пустых коллекций, `omitempty`, точности чисел и внешней схемы по [руководству по переходу](https://go.dev/doc/jsonv2-migration). Не повышай минимальную версию Go ради v2. |
| CSV по распространённой грамматике | `encoding/csv` | Если нужен конкретный диалект или поведение, которого пакет не поддерживает. Ограничь собственный разбор точно описанной грамматикой. |
| HTTP-клиент или сервер | `net/http` | Если подтверждённая потребность не покрывается стандартным API или проект уже использует совместимую библиотеку. Общие правила отмены, сроков выполнения, освобождения ресурсов и ограничения повторов описаны в [надёжности и производительности](reliability-and-performance.md). |
| Пути | `path/filepath` для путей файловой системы текущей ОС, `path` для путей формата или протокола с разделителем `/` | Если файловый API или протокол задаёт специальные правила. Очистка строки сама по себе не доказывает, что путь останется внутри разрешённого корня. |
| Криптография и TLS | [`crypto/tls`](https://pkg.go.dev/crypto/tls) для TLS, [`crypto/x509`](https://pkg.go.dev/crypto/x509) для сертификатов и их проверки, [`crypto/rand`](https://pkg.go.dev/crypto/rand) для криптографически стойкой случайности, нужный пакет `crypto/...` для поддерживаемого стандартной библиотекой примитива | Выбирай по требуемому протоколу, алгоритму и формату ключа или сертификата, совместимости и модели угроз. Если стандартный API не покрывает контракт, выбери проверенную библиотеку. Не реализуй криптографические примитивы самостоятельно. |
| Сложный Markdown | Поддерживаемый парсер нужного диалекта | Собственная обработка оправдана только для явно ограниченного формата, если совместимость с полной грамматикой не требуется и ограничения проверяются. |
| YAML | Поддерживаемый сторонний парсер, поскольку формат не предоставляется стандартной библиотекой Go | Сравни поддержку необходимого подмножества, совместимость схемы и обработку ошибок. Не замещай полноценный YAML упрощённым собственным разбором. |
| Небольшой CLI | Стандартный `flag` или простая обработка `os.Args`, если они покрывают контракт | Для вложенных команд, сложной грамматики, генерации справки или других подтверждённых потребностей сравни текущие зависимости и сторонние варианты. |

Не существует требования выбирать только стандартную библиотеку или добавлять библиотеку для каждой операции. Для простой операции цена новой зависимости может быть выше её пользы. Для форматов, протоколов и алгоритмов со сложной грамматикой или высокими последствиями ошибки предпочтительнее зрелая реализация, если она соответствует контракту.

## Оцени новую зависимость

Сопоставь полную стоимость зависимости со стоимостью поддерживаемой собственной реализации, включая обработку краёв формата, обновления, исправления уязвимостей и совместимость. Проверь факты по документации, коду и метаданным конкретной версии.

- Поддерживает ли API каждое необходимое поведение без скрытой потери данных или изменения контракта.
- Совместима ли лицензия с распространением проекта и его правилами.
- Есть ли понятные признаки сопровождения, опубликованные версии, документация и политика обратной совместимости.
- Известны ли уязвимости в выбранной версии и как проект сможет получать обновления безопасности.
- Какие транзитивные зависимости, платформенные ограничения, CGO и требования к сборке она добавляет.
- Какова стоимость интеграции, диагностики, обновления и дальнейшего сопровождения API.

Не суди о пригодности только по популярности, свежести последнего коммита или короткому примеру. Учитывай конкретную версию и фактический путь вызова. Согласуй добавление новой зависимости по действующим правилам проекта до изменения списка зависимостей.

## Если проект использует модули Go

Не предполагай наличие `go.mod` и не создавай модуль только ради применения этого референса. Если модули уже используются:

- Сохраняй заявленную минимальную версию Go и совместимость со всем поддерживаемым диапазоном. Не повышай её только потому, что выбранная библиотека использует более новую возможность.
- При согласованном изменении используй Go-инструменты управления модулями, проверь изменения в `go.mod` и `go.sum` и включи оба файла в изменение, когда они затронуты. `go.sum` содержит контрольные суммы модулей.
- Проверяй транзитивные изменения, несовместимые обновления и заметки выпуска конкретной версии. Удаляй неиспользуемые зависимости средствами проекта, например через `go mod tidy`, и просматривай все его изменения.
- Используй предусмотренные проектом проверки и доступные средства проверки уязвимостей. Не добавляй для этого новый инструмент, зависимость или CI без отдельного согласования.

Документация Go описывает [управление зависимостями](https://go.dev/doc/modules/managing-dependencies), включая `go.mod`, контрольные суммы `go.sum` и очистку списка модулей через `go mod tidy`. Рекомендации Go по [безопасности](https://go.dev/doc/security/best-practices) включают проверку зависимостей и уязвимостей. Для выбора полезен также разбор [стоимости программных зависимостей](https://research.swtch.com/deps), который следует применять как критерии оценки, а не как обязательный запрет на библиотеки.

Документация стандартной библиотеки: [`encoding/json`](https://pkg.go.dev/encoding/json), [`encoding/csv`](https://pkg.go.dev/encoding/csv), [`net/http`](https://pkg.go.dev/net/http), [`path`](https://pkg.go.dev/path), [`path/filepath`](https://pkg.go.dev/path/filepath) и [`crypto`](https://pkg.go.dev/crypto).
