# Проектирование Go-кода

Выбирай структуру, которую проще всего правильно читать, менять и использовать. Число строк не измеряет простоту. Сначала проверь, какую проблему решает предлагаемая граница или абстракция. [Go Style Guide](https://google.github.io/styleguide/go/guide) полезен как набор рекомендаций о ясности и простоте, но описывает стиль Google, а не обязательный стандарт любого Go-проекта.

## Границы и связность

- Держи вместе код, который меняется по одной причине и владеет общими правилами. Пакет должен представлять понятную возможность, а его экспортируемый API — нужный внешний контракт.
- Направляй зависимости к владельцу правила. Не создавай второй источник истины, слой-переадресатор или цикл импортов ради симметрии. Оставляй зависимости и передачу данных явными.
- Выделяй пакет, интерфейс или слой, когда он задаёт реальную границу ответственности, данных или замены реализации. Не навязывай Clean Architecture, SOLID, DDD или каталогную структуру независимо от размера и потребностей задачи.
- Не вводи движок, DSL, плагинность, настройки и общую платформу для гипотетических потребителей. При этом отсутствие второго потребителя не отменяет абстракцию, необходимую существующему контракту.
- Не дроби функции и файлы по фиксированным числовым пределам. Разделяй их, когда это проясняет самостоятельную задачу или позволяет безопасно менять конкретную часть.

Для типичных Go-пакетов и модульной структуры см. [Organizing a Go module](https://go.dev/doc/modules/layout). Имена пакетов и сторона, на которой определяют интерфейс, описаны в [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).

## Паттерны по необходимости

Используй паттерн, когда он делает существующее требование яснее. Сначала назови проблему, затем критерий применения и простейший механизм, который уже покрывает задачу.

| Проблема | Паттерн | Критерий применения | Более простой вариант |
| --- | --- | --- | --- |
| Выбор алгоритма затрудняет растущий набор режимов | Strategy | Варианты независимы, а условия выбора разрастаются | `switch` для небольшого стабильного выбора |
| Контракт внешнего API отличается от внутреннего | Adapter | Преобразование нужно изолировать на реальной границе | Прямой вызов, если преобразование однозначно и встречается в одном месте |
| Общее поведение приходится повторять вокруг многих обработчиков | Decorator | Обёртки должны независимо сочетаться | Обычный код до и после единственного вызова |
| Правила создания расползаются по вызовам | Factory | Нужно проверять инварианты или выбирать один из нескольких вариантов | Функция-конструктор или литерал структуры |
| Замена реализации или ресурса зависит от вызывающего кода | Явное внедрение зависимости | Передача зависимости соответствует реальной границе | Прямое использование конкретной зависимости, когда замена и передача не нужны |
| Прикладной код не должен зависеть от деталей доступа к данным | Repository | Контракт хранения отделяет реальное хранилище или его семантику | Вызов конкретного клиента хранения без дополнительного интерфейса |
| Одно обрамление нужно применять к множеству обработчиков | Middleware | Обработчики проходят согласованную композицию обрамлений | Обычная функция вокруг одного обработчика |
| Обработка состоит из отдельных упорядоченных этапов | Pipeline | Этапы имеют самостоятельный смысл или собственные правила остановки | Последовательные вызовы функций для короткой фиксированной цепочки |
| Параллельную работу нужно ограничить по числу исполнителей | Worker Pool | Задачи независимы, а число одновременных задач должно быть ограничено | Последовательный цикл для малого объёма или уже ограниченного числа задач |
| Необходимо обеспечить разрешённые переходы между состояниями | State Machine | Поведение зависит от предыдущего состояния, и допустимы не все переходы | Булево значение или простой `switch`, если переходы очевидны |
| Необязательные параметры конструктора трудно поддерживать | Functional Options | Опций много, они независимы, а вызовы нужно наращивать совместимо | Параметры или конфигурационная структура для короткого фиксированного набора |
| Действие требуется передавать как данные | Command | Действия нужно ставить в очередь, сохранять или выбирать отдельно от вызова | Прямой вызов функции или метода для немедленного действия |

Не вводи интерфейс и фабрику для одной функции без границы ответственности. В Go интерфейс на стороне потребителя может быть оправдан и при одной реализации, если он отделяет реальное хранилище или сервис. Не создавай конечный автомат для произвольного флага. Общие правила интерфейсов описаны в [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).

## Исправляй причину

Если проблема выявилась на редком вводе, исправляй общее правило, которое ошиблось. Не добавляй ветку под конкретный пример, не подавляй отказ, не ослабляй проверки или тесты и не маскируй потерю данных fallback-ом. Резервный путь оправдан, когда он входит в контракт и имеет определённое поведение при отказе. `sleep` не заменяет синхронизацию, а безграничные повторы не исправляют условие сбоя.

Сохраняй существующие гарантии и проверяемые контракты. Если существенный компромисс меняет их или выходит за согласованный объём, сначала согласуй его по правилам проекта. Не оставляй обходной путь, временную ветку и мёртвую реализацию после того, как исправление завершено.

## Литералы и комментарии

Не выноси каждый литерал в конфигурацию или именованную константу. Именуй значение, когда имя объясняет смысл или выражает общий инвариант. Изменяемые пользовательские, тестовые и средовые данные не должны попадать в производственную логику. Фиксированные значения протокола допустимы, если их смысл очевиден.

Пиши комментарий о причине, контракте или инварианте, который неясен из кода. Не пересказывай очевидное поведение. Простота, явный поток данных и отсутствие ненужных уровней абстракции согласуются с принципами [Go Style Guide](https://google.github.io/styleguide/go/guide).
