# Идиоматичный Go

Выбирай конструкцию по её семантике и поддерживаемой версии Go. Сверяйся с кодом рядом и контрактом задачи. Стилистические руководства помогают принять решение, но не заменяют требования проекта. [Effective Go](https://go.dev/doc/effective_go) написан для выпуска 2009 года и не описывает многие современные возможности языка.

## Пакеты и API

- Держи связанные типы и поведение вместе. Имя пакета должно быть коротким и предметным. Не повторяй его в именах экспортируемых сущностей: `parser.Token`, а не `parser.ParserToken`. Не создавай `util`, `common` или `misc` как места для несвязанных функций.
- Экспортируй только те имена, которые входят в нужный внешний контракт. Комментарий к экспортируемому имени объясняет его назначение и существенное поведение. Форматируй код `gofmt`, а не ручным выравниванием.
- Используй `internal/`, когда нужно запретить импорт пакета из-за пределов поддерева, содержащего этот каталог. Не добавляй его механически для сокрытия обычного внутреннего кода.

Рекомендации по именам, комментариям и границам API есть в [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) и [Organizing a Go module](https://go.dev/doc/modules/layout).

## Типы и интерфейсы

- Начинай с конкретного типа. Определяй небольшой интерфейс в пакете-потребителе, когда поведение требуется отделить на реальной границе или заменить при вызове. Не добавляй интерфейс на стороне реализации только ради моков и не объявляй его до появления потребителя.
- Одна реализация сама по себе не мешает интерфейсу, если граница уже есть, например хранилище за контрактом прикладной операции. Без такой границы конкретный тип обычно яснее.
- Предпочитай композицию и нулевое значение, которым безопасно пользоваться. Если корректное состояние требует конструктора или порядка инициализации, явно зафиксируй инвариант в API.

## Значения, указатели и владение

- Используй `*T` как тип получателя, если метод меняет `T`, `T` велик или содержит синхронизирующее состояние. Значение подходит небольшому неизменяемому типу. Выбрав получатель для типа, придерживайся одного подхода для его методов. Не передавай указатель функции только ради экономии нескольких байт.
- Не копируй `sync.Mutex` после первого использования. Это же ограничение относится к копии структуры, если при этом копируется уже использованный мьютекс. Учитывай собственные ограничения на копирование и у других типов. [Контракт `sync.Mutex`](https://pkg.go.dev/sync#Mutex).
- Копирование структуры с полем типа `map[string]string`, срезом или указателем копирует поля по значению, поэтому данные по ссылке могут остаться общими. Такая копия допустима, если разделяемое владение соответствует контракту. Решай, создавать ли отдельную копию данных или сохранять общую ссылку, с учётом контракта и конкурентного доступа. См. [представление значений в спецификации Go](https://go.dev/ref/spec#Representation_of_values).
- У интерфейса есть динамический тип и значение. Интерфейс с типизированным nil-указателем не равен `nil`: `var p *T; var v interface{} = p; v != nil`. Возвращай настоящий nil-интерфейс при отсутствии результата, если именно это обещает API.
- Порядок обхода карт не определён. Если порядок влияет на вывод, выбор результата или внешний контракт, задай его явно.

Подробности о выборе получателя, копировании и nil есть в [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).

## Обобщённые типы и функции

Сначала напиши конкретную функцию или тип. Добавляй параметры типов, когда один и тот же алгоритм осмысленно работает с несколькими типами, особенно с контейнерами, где операции не зависят от конкретного элемента. Для поведения с несколькими реализациями используй интерфейс, если контракт описывает действия, а не общий тип данных. Не вводи обобщённые типы и функции ради устранения нескольких коротких повторов или гипотетического повторного использования. Ориентиры приведены в официальной статье [When To Use Generics](https://go.dev/blog/when-generics).

## Внешние данные и сериализация

Сохраняй различия, которые несёт схема. В JSON отсутствующее поле, `null`, нулевое значение и пустая коллекция могут иметь разный смысл. Стабильный `encoding/json/v2` доступен начиная с Go 1.27. Для нового применения рассматривай v2, если минимальная поддерживаемая версия Go включает его и его семантика соответствует контракту. Пакет v1 рекомендует v2 для новых случаев, но остаётся поддерживаемым, а переход не обязателен. Сохраняй v1 для существующего контракта или совместимости, которой v2 не обеспечивает. См. [Go 1.27 Release Notes](https://go.dev/doc/go1.27) и рекомендацию в документации [`encoding/json`](https://pkg.go.dev/encoding/json).

По умолчанию в v1 nil-срез и nil-карта кодируются как `null`; в v2 nil-срез кодируется как пустой массив, nil-карта — как пустой объект, а nil `[]byte` — как пустая строка `""`. `omitempty` в v1 пропускает поле, если исходное значение Go считается пустым, а в v2 — если оно кодируется как пустое значение JSON. Сверяй точное поведение и варианты настройки с [документацией `encoding/json/v2`](https://pkg.go.dev/encoding/json/v2) и [руководством перехода с v1 на v2](https://go.dev/doc/jsonv2-migration). Не полагайся на эквивалентность этих форм и учитывай внешнюю схему.

При разборе чисел учитывай точность и диапазон целевого типа. В API `encoding/json` v1 разбор JSON в `any` по умолчанию представляет числа как `float64`; для сохранения числового текста используй `Decoder.UseNumber` или разбирай значение в подходящий конкретный тип. Не теряй неизвестные или дополнительные данные, если совместимость схемы требует их сохранить.

Рекомендации о nil и пустых срезах приведены в [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).

## Совместимость с версией Go

Проверяй минимальную поддерживаемую версию в `go.mod`, конфигурации сборки, CI и целевых окружениях. Используй только синтаксис и API, доступные этой версии. Если сведения о версиях расходятся, уточни фактический контракт проекта до изменения инструментария Go. Не закрепляй текущую версию Go в этом руководстве как постоянное требование. См. [директиву `go` и версию языка в `go.mod`](https://go.dev/doc/modules/gomod-ref#go).
