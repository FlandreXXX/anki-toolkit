# Практики и организация Go-тестов

Этот справочник описывает размещение тестов, API и способы запуска в Go. Гарантию и уровень проверки выбирай по [проектированию тестов](test-design.md).

## Файлы и пакеты

- Размещай модульные тесты, тесты для фаззинга и бенчмарки в `*_test.go` рядом с проверяемым
  пакетом. В том же каталоге используй `package foo` для доступа к внутренним инвариантам
  или `package foo_test` для проверки через экспортируемый API. Тесты отдельного каталога
  образуют отдельный пакет. Не экспортируй детали реализации только ради тестов.
- Храни устойчивые локальные тестовые данные в `testdata/`.
- Интеграционный тест одного пакета может оставаться рядом с ним. Выноси межкомпонентные и
  E2E-сценарии в отдельные каталоги вроде `tests/integration/` и `tests/e2e/`, когда границы
  и масштаб делают их понятнее. Выбирай расположение по границам сценария и соглашениям проекта.
- Используй обычные имена `TestXxx`, `BenchmarkXxx`, `FuzzXxx` и `ExampleXxx`, которые распознаёт `go test`. Соблюдай формат и именование Go-пакета.

## Читаемые проверки

- Проверяй наблюдаемое поведение, состояние, побочные эффекты и семантику отказа, важные для
  контракта. Один метод может иметь несколько независимых поведений, а поведение может
  затрагивать несколько методов.
- Табличный тест с `t.Run` подходит, когда случаи проверяют одно правило общей логикой. Давай
  подслучаям имена, отражающие условие или границу; сохраняй входы и ожидаемые результаты
  независимыми и понятными. Не объединяй разные контракты ради одной функции и не заполняй
  таблицу однотипными строками без новой гарантии.
- При отказе показывай существенный вход, фактическое значение (`got`) и независимое ожидаемое значение (`want`).
- Используй `t.Helper` для небольшого помощника, если он проясняет подготовку или повторяемую
  проверку и сохраняет место вызова в диагностике. Не прячь основное утверждение за
  универсальной библиотекой проверочных утверждений. Выбирай `t.Error`/`t.Errorf`, когда остальные
  независимые проверки ещё полезны; `t.Fatal`/`t.Fatalf` — когда продолжение невозможно,
  например после ошибки подготовки. Методы `FailNow` и `Fatal` должны вызываться из горутины
  теста, а не из созданной тестом фоновой горутины.

## Изоляция, время и параллельность

- Создавай временный каталог через `t.TempDir`. Он удаляется после завершения теста и его
  подтестов. Функции `t.Cleanup` выполняются после теста и его подтестов в порядке,
  обратном регистрации.
- При завершении фоновой работы сначала подай сигнал отмены или остановки, затем дождись
  завершения горутин и освободи ресурсы. Если ресурс нужно закрыть для разблокирования
  горутины, закрой его перед ожиданием. Начиная с Go 1.24 передавай фоновой работе
  `t.Context()` и жди завершения в функции `t.Cleanup`. Go отменяет этот контекст перед
  запуском функций очистки. В более ранних версиях явно отменяй контекст перед ожиданием
  в одной функции очистки. Если функции раздельные, зарегистрируй ожидание раньше отмены,
  чтобы отмена выполнилась первой.
- Изолируй окружение и глобальное состояние. `t.Setenv` и `t.Chdir` меняют состояние всего
  процесса и не могут вызываться в параллельном тесте или тесте с параллельным предком. Не
  включай `t.Parallel` для сценария, пока общие файлы, переменные окружения, рабочий каталог,
  случайность и фоновые ресурсы не изолированы.
- Не используй `time.Sleep` для угадывания момента выполнения конкурентного кода. Координируй
  события каналами и другими примитивами синхронизации. Для самодостаточных сценариев с
  управляемым временем используй `synctest.Test` в Go 1.25 и новее. Он запускает проверку
  в изолированной среде с виртуальными часами. Избегай зависимостей от внешних горутин,
  сети и процессов. Вызывай `synctest.Wait()` внутри этой среды. Он ждёт, пока остальные
  горутины в ней окажутся устойчиво заблокированы, например на канале, созданном в той же
  среде. Блокировки на мьютексах, вводе-выводе и системных вызовах не считаются устойчивыми.
  Для проверки завершения горутины используй явный сигнал о завершении.
- У внутреннего `*testing.T`, который `synctest.Test` передаёт проверке, нельзя вызывать
  `Run`, `Parallel` и `Deadline`. Запускай табличные подтесты через внешний `t.Run` и создавай
  изолированную среду внутри каждого случая, которому она нужна.
- `-race` обнаруживает гонки данных только в выполненных путях и не доказывает их полного
  отсутствия. Запускай его по риску и возможностям среды, а результат описывай именно как
  прогон под детектором гонок.

## Реальные реализации и заменители

- Используй `net/http/httptest` для локальных HTTP-сценариев и `testing/fstest` для проверок
  файловых систем. Модульные тесты изолируй от внешней сети и пользовательских данных.
  Для выбора заменителя сверяйся с [проектированием тестов](test-design.md).
- Проверяй реальные границы интеграции и E2E в отдельном окружении с синтетическими или явно
  разрешёнными данными. Если переносимость входит в контракт, проверяй окружения, которые
  поддерживает проект. Docker можно использовать для изоляции реальных внешних зависимостей.

## Фаззинг, свойства и бенчмарки

- Проверяй независимый инвариант на сложных входах, например при разборе и сериализации.
  Делай цель фаззинга быстрой, детерминированной и независимой от общего состояния. Go может
  вызывать её параллельно и в произвольном порядке. Начни с нескольких характерных
  начальных входов. Для входа вне контракта цели допустим `t.Skip`. Если отклонение входа
  входит в контракт, проверяй ожидаемый отказ.
- Обычный `go test` запускает начальные входы из `F.Add` и `testdata/fuzz/<FuzzName>/` в
  каталоге пакета. Активный поиск новых входов включается через `-fuzz`. Ограничивай
  длительность поиска через `-fuzztime` и указывай в отчёте, какой режим использован.
- При обнаружении отказа Go записывает воспроизводящий вход в `testdata/fuzz/<FuzzName>/`,
  а если запись туда недоступна, сохраняет его в кэше фаззинга. Обычный прогон этот
  кэш не читает. Если вход нужен по [критериям регрессии](regression-and-coverage.md),
  убедись, что минимальный случай есть в `testdata/fuzz/<FuzzName>/` или `F.Add` и
  выполняется обычным прогоном без `-fuzz`.
- `BenchmarkXxx(*testing.B)` измеряет выбранную операцию, но не заменяет проверку корректности.
  Запускай бенчмарк, когда есть измеряемый вопрос. Сравнивай сопоставимую работу и при
  необходимости собирай данные о выделениях через `-benchmem`.

## Запуск и смысл флагов

Подбирай команду по структуре проекта, поддерживаемой версии Go и принятой форме запуска. Не предполагай, что каждый репозиторий является модулем или поддерживает `go test ./...`.

- `-run` выбирает тесты и подтесты по регулярному выражению. Используй его для точечной
  диагностики и выполняй полный прогон, когда он нужен для проверки изменения.
- При запуске по списку пакетов `go test` может кэшировать успешный результат. Флаг
  `-count=1` явно отключает кэш результатов. Запуск тестов текущего каталога без аргумента
  пакета также выполняется без кэша результатов.
- `-cover` выводит долю выполненных операторов, `-coverprofile` включает измерение покрытия
  и записывает профиль для разбора по участкам кода. По умолчанию анализируется тестируемый
  пакет. `-coverpkg` задаёт шаблоны путей импорта пакетов для межпакетного измерения.
  Выводы делай по [правилам интерпретации покрытия](regression-and-coverage.md).
- `-shuffle` с выведенным начальным значением помогает воспроизвести зависимость от порядка.
  `-count` повторяет обычные тесты, включая начальный корпус. Применяй повторение и
  перемешивание для диагностики конкретного риска и устраняй причины недетерминизма.

Сверяй доступность API и флагов с поддерживаемой версией инструментария Go. В Go 1.24
`testing/synctest` был экспериментальным. Стабильный API доступен с Go 1.25. Для более
ранних версий используй явную синхронизацию или доступную в проекте абстракцию времени.
Точные команды и обязательные проверки бери из инструкций проекта, если они есть.

## Первичные источники

- [Пакет `testing`](https://pkg.go.dev/testing) — тесты, подтесты, очистка, параллельность, фаззинг и API бенчмарков.
- [Пакет `testing/synctest`](https://pkg.go.dev/testing/synctest) — изолированная среда, управляемое время и `Wait`.
- [Go 1.25 Release Notes](https://go.dev/doc/go1.25#new-testingsynctest-package) — переход `testing/synctest` от эксперимента к стабильному API.
- [Документация флагов `go test`](https://pkg.go.dev/cmd/go#hdr-Testing_flags) — кэш, покрытие, выбор тестов, фаззинг и повторы.
- [Go Fuzzing](https://go.dev/doc/security/fuzz/) — начальный корпус, активный поиск и сохранение воспроизводящих входов.
- [Go Style Decisions: Useful test failures](https://google.github.io/styleguide/go/decisions#useful-test-failures)
  и [Table-driven tests](https://google.github.io/styleguide/go/decisions#table-driven-tests) —
  рекомендации Google по диагностике и табличным тестам.
- [The Go Blog: The cover story](https://go.dev/blog/cover) — семантика измерения покрытия Go.
