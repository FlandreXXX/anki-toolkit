# Проектирование и проверка тестов

Скилл определяет, какие гарантии проверять и каких свидетельств достаточно. Он применим самостоятельно. Если доступен Ponytail, общая инженерная методология и независимое ревью остаются за ним. Ориентир на одну небольшую проверку не заменяет проверки других самостоятельных существенных рисков; необходимые для проверки фикстуры допустимы.

## Короткий маршрут

1. Установи контракт поведения и последствия его нарушения.
2. Найди существующие проверки и владельца соответствующей гарантии.
3. Выбери значимый пробел, способ проверки и наиболее узкий уровень, который достоверно проверит нужный контракт.
4. Переиспользуй или минимально дополни набор; выполни применимые проверки и укажи, что они действительно доказывают.

Загружай подробности только по текущему решению:

- [Проектирование тестов](references/test-design.md) — наблюдаемое поведение, независимый эталон, риски, уровень и достоверность заменителей.
- [Практики Go-тестов](references/go-testing.md) — размещение тестов, API и способы запуска в Go.
- [Регрессии и покрытие](references/regression-and-coverage.md) — решение о добавлении регрессионной проверки и интерпретация покрытия.

Дополняй скилл доступными практиками языка, например `go-best-practices` для Go. Соблюдай маршрутизацию проекта и бери фактические команды у локального владельца проверок. Если таких инструкций нет, опирайся на поручение и штатные средства проекта.

Временные эксперименты и их свидетельства размещай по правилам проекта; если доступен `git-workflow`, место и границы хелперов определяет его [контракт артефактов](../git-workflow/references/pr-lifecycle.md). Хелпер не подменяет проверяемую реализацию или обязательную проверку.

Соблюдай порученный объём и полномочия. При ревью вноси правки только по отдельному поручению.
