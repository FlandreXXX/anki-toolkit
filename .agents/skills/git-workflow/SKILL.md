# Git-процесс рабочей задачи

## Назначение

Скилл — **единственный владелец** общей процедуры Git/GitHub для текущей
рабочей копии: рабочая ветка, индекс, коммит, push, проверка удалённого состояния,
создание и обновление PR, структурированное описание PR, Draft/Ready, отдельно
разрешённый merge и очистка после merge.

Скилл не владеет:

- содержанием работы: что именно нужно изменить, определяет сама задача и
  постоянные документы репозитория (`AGENTS.md`, документация затронутой области);
- набором проверок репозитория — их владельцы перечислены в `AGENTS.md`, в
  `.agents/context/03-VERIFICATION.md` и в самом CI репозитория;
- инженерными практиками и независимым ревью — это внешние владельцы (например,
  Ponytail); они не расширяют полномочия этого скилла и не отменяют согласованный
  контракт текущей задачи;
- чужими PR и чужими ветками: скилл обслуживает текущую задачу.

Не создавай второго владельца этой процедуры в `AGENTS.md` или в другом скилле.
Скилл не создаёт собственную обёртку над `git`/`gh`, своего CLI, автомата
состояний, сохраняемого журнала публикации или отдельного хранилища состояния.
Проверка формата описания PR — отдельная детерминированная проверка
`.github/scripts/pr-body-lint/main.go`, а не замена общей процедуры публикации.
Формат, история и публикация накопительного отчёта CodeRabbit принадлежат
[`../coderabbit-review/references/review-report.md`](../coderabbit-review/references/review-report.md):
это отдельный комментарий PR, а не часть описания.

## Контракт маршрутизации

Скилл **не требует** буквального имени скилла или специальной фразы. Он
применяется, когда работа достигает жизненного цикла Git/GitHub:

- создание или продолжение рабочей ветки;
- подготовка индекса;
- commit;
- push;
- создание, обновление или перечитывание PR;
- Draft/Ready;
- проверка удалённого состояния, CI и ревью перед передачей пользователю;
- обновление base и разрешение конфликтов;
- отдельно разрешённый merge;
- уборка после merge;
- продолжение уже начатой публикации, в том числе в среде без локального
  `git`/`gh` — через GitHub MCP/API.

Явные запросы пользователя — «закоммить», «запушь», «создай PR», «обнови PR»,
«слей PR», «сделай Draft PR» — маршрутизируются сюда же.

Скилл **не активируется** для:

- простого объяснения Git/GitHub без изменений;
- чтения истории, веток или чужого PR только ради исследования, если жизненный
  цикл Git не выполняется;
- обычного ревью кода — им владеет ревьюер, а не этот скилл;
- задачи по изменению самого этого скилла как повода выполнить дополнительные
  действия GitHub сверх текущей задачи.

## Контракт конечного состояния: коммит не равен публикации

Это главный контракт скилла.

Если обычная задача репозитория предполагает публикацию результата и пользователь
явно не ограничил область задачи локальной работой, состояние

```text
есть новый локальный коммит
удалённая ветка его не содержит
```

**не является** завершением задачи. После коммита рабочий процесс обязан без
дополнительного сообщения пользователя «теперь push» продолжить публикацию и
довести её до подтверждённого удалённого состояния.

Ожидаемая цепочка обычной публикуемой задачи:

```text
изменение
→ применимые проверки
→ проверенный индекс
→ коммит
→ push текущей рабочей ветки
→ проверка точного удалённого HEAD
→ создание или актуализация Draft PR с описанием по `references/pr-body.md`
→ повторное чтение и проверка опубликованного PR
→ передача пользователю на ревью
```

Merge в этот автоматический жизненный цикл **не входит**: он выполняется только
по отдельной текущей явной команде пользователя (см.
[`references/pr-lifecycle.md`](references/pr-lifecycle.md), § «Merge»).

Допустимое переопределение — только явное указание пользователя в текущем запросе:
«только локально», «только коммит», «не push». Такое указание ограничивает
цепочку ровно настолько, насколько сказано, и относится к текущей задаче.

Локальный код возврата push сам по себе не является доказательством конечного
состояния, и устаревшая ссылка слежения за удалённой веткой — тоже. Публикация
подтверждена только точным сравнением ожидаемого локального HEAD с фактическим SHA
соответствующей удалённой ветки, прочитанным из удалённого репозитория (см.
[`references/publication.md`](references/publication.md)).

## Штатные инструменты

Граница инструментов:

- штатный `git` — локальная история, `status`/`diff`, ветка, подготовка индекса,
  коммит, fetch, merge/rebase по разрешённой политике, push и чтение удалённой
  ссылки;
- `gh` — изменения GitHub текущей задачи: создание/обновление PR, Draft/Ready и
  разрешённый merge, когда локальный CLI доступен;
- GitHub MCP/коннектор — структурированное чтение удалённого состояния GitHub, а
  при работе без локальной рабочей копии и CLI — также публикация коммита и PR с
  теми же проверками целевой ссылки, точного SHA, структуры описания и повторного
  чтения; этот путь не обходит ни проверку описания, ни сравнение SHA;
- `gh ... --json` — допустимый запасной вариант и короткая проверка состояния.

Версионно-зависимые операции не описываются как вечный контракт: конкретную
версию `gh`, имена полей и флаги проверяй по фактическому интерфейсу установленного
инструмента там, где это действительно нужно, а не по памяти и не по тексту этого
скилла.

## Инварианты

- Одна самостоятельная задача — одна рабочая ветка и один PR. Продолжение той же
  работы использует прежнюю ветку и прежний PR.
- Не работай напрямую в ветке по умолчанию: это постоянное правило репозитория
  (`AGENTS.md`). Ветки не переключаются молча.
- Не считай локальный коммит доказательством публикации.
- Не считай код возврата push доказательством удалённого конечного состояния без
  чтения фактической удалённой ссылки.
- Разрешение на коммит и push не разрешает ни Ready, ни merge. Draft — состояние
  по умолчанию; Ready — только по явному разрешению или согласованному контракту
  текущей задачи; merge — только по отдельной текущей явной команде.
- Не создавай дублирующий PR для того же репозитория/base/head.
- Не закрепляй в тексте номер PR, имя ветки, SHA, номер этапа, абсолютные локальные
  пути и имя пользователя: ни в этом скилле, ни в его справочных документах.
- Не подмешивай и не уничтожай неизвестные пользовательские изменения и чужую
  подготовку индекса.
- Force-push, переписывание опубликованной истории и удаление неизвестных удалённых
  ветвей требуют отдельного явного основания в текущем запросе.
- Описание PR передаётся проверенным файлом; в режиме без локального CLI —
  проверенным полным значением через API с обязательным повторным чтением.
- Не ослабляй применимые проверки репозитория и не выдумывай фиктивные проверки
  ради зелёного результата. Обход проверок запрещён.
- Не считай успешный прогон проверки доказательством для другой редакции описания
  или другого HEAD.
- Не расширяй область ответственности скилла инфраструктурой «на будущее».

## Подробный порядок действий

- [`references/publication.md`](references/publication.md) — ветка, подготовка
  индекса, коммит, push, точная проверка удалённого состояния, протокол
  неизвестного результата сетевой операции и запрещённые операции публикации.
- [`references/pr-body.md`](references/pr-body.md) — содержательная структура
  описания PR, пять обязательных разделов, правила непустоты, предел 10 000
  кодовых точек Unicode и локальная проверка описания.
- [`references/pr-lifecycle.md`](references/pr-lifecycle.md) — идентификация PR,
  источник описания, публикация и повторное чтение, Ready, merge, конфликты с base,
  очистка и роль CI.

Читай нужный справочный документ перед выполнением соответствующего шага:
`SKILL.md` задаёт контракт и границы, справочные документы владеют порядком действий.
