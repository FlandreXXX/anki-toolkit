# Жизненный цикл PR: описание, Draft/Ready, merge, конфликты, уборка

Этот файл владеет порядком действий после подтверждённой публикации коммита.
Контракт и границы задаёт `SKILL.md`; постусловие push описано в
[`publication.md`](publication.md); структура описания — в [`pr-body.md`](pr-body.md).

## 1. Идентичность PR

У обычной самостоятельной задачи репозитория **один** PR.

1. Установи текущий репозиторий, ожидаемые base и head, включая репозиторий
   владельца head. Перечисли открытые PR по base/head через GitHub API/коннектор
   либо
   `gh pr list --base <base> --head <head> --limit <достаточный лимит> --json number,baseRefName,headRefName,headRepository,headRepositoryOwner`.
   Проверь полноту выдачи и фактические репозиторий/base/head каждого кандидата:
   одинаковые имена веток в разных форках не доказывают идентичность. `gh pr view`
   без номера показывает один PR ветки и не доказывает единственность.
2. Для выбора существующего PR требуется ровно одно совпадение. При нуле,
   неоднозначности или неполной выдаче останови операцию над существующим PR;
   не угадывай и не переключайся на другой PR. При единственном совпадении
   перечитай его по номеру и используй этот номер для дальнейших операций.
3. Для отдельной операции создания нового PR отсутствие совпадений сначала
   устанавливается полной выдачей; дубликат для той же пары не создавай. Пока не
   создавай PR: сначала подготовь и проверь описание по порядку ниже. Отсутствующий
   PR — допустимое состояние подготовки нового PR.

Не создавай новый PR только потому, что началась следующая фаза той же рабочей
задачи, и не переключайся на другой PR.

## 2. Локальные артефакты задачи и источник описания PR

Одна самостоятельная публикуемая задача использует один смысловой каталог,
одну рабочую ветку и один PR. Продолжение того же PR использует прежний каталог.
При работе с локальной рабочей копией располагай артефакты от корня рабочей
копии — владельца задачи, а не от произвольного текущего каталога:

```text
.agents/local/pr/<смысловой-идентификатор>/
├── meta/body.md
├── scripts/
├── reports/
└── worktrees/
```

`<смысловой-идентификатор>` — короткий смысловой идентификатор текущей рабочей
задачи, а не номер PR, SHA или номер этапа. Содержимое описывает фактическое
состояние задачи и не хранит временных идентификаторов, разового плана и
стенограммы.

`meta/` хранит источник описания и только необходимую метаинформацию, позволяющую
найти связь с задачей; `scripts/` — временные хелперы; `reports/` — отчёты,
заметки и свидетельства, в том числе испытаний; `worktrees/` — изолированные
рабочие деревья и временные тестовые репозитории. Создавай только используемые
категории, без обязательного манифеста или пустых файлов. Для связанного worktree
явно установи и передай исполнителю корень артефактов основной задачи: один PR
не получает параллельных источников описания. У другого репозитория и его тестовых
PR — собственные каталоги в соответствующих рабочих копиях.

Хелперы могут готовить входы, воспроизводить ошибки, вызывать проверяемый код и
сравнивать результаты с независимым эталоном. Они не подменяют продукт, линтер,
обязательную проверку или работу агента и не исправляют вывод дефектной реализации
ради успеха. Постоянная логика продукта и его тестов принадлежит отслеживаемым
файлам, а не локальному хелперу.

Единственный источник описания PR — `meta/body.md` этого каталога. Не публикуй
локальные артефакты и не сохраняй в них секреты.

Правила:

- этот тип артефактов закрыт правилом игнорирования `.gitignore`; правило должно
  быть минимально достаточным и не скрывать отслеживаемые файлы (`AGENTS.md`,
  `.agents/skills/**`);
- путь действительно игнорируется и не отслеживается — это проверяется фактом
  (`git check-ignore -v <путь>`, `git ls-files <путь>`), а не предположением;
- генератор, схема или шаблонизатор описания не вводится: Markdown-файла
  достаточно;
- файл полностью формируется и **перечитывается** до публикации;
- файл сохраняется минимум до подтверждённого повторного чтения опубликованного PR
  и не удаляется, пока результат операции неизвестен.

### Поиск каталога при возобновлении работы

Возобновление известной задачи в новом сеансе начинается с поиска уже
существующего каталога, а не с создания нового имени. Порядок:

1. Установи известную связь задачи с PR и веткой по § 1 и по фактической
   метаинформации, которой уже располагает сеанс: переданный пользователем путь,
   явно названный идентификатор, номер PR, имя ветки. Сходство имени каталога
   идентичность не доказывает и основанием выбора не является.
2. Найди кандидатов в `.agents/local/pr/` основной рабочей копии и проверь у
   каждого фактическое соответствие: наличие `meta/body.md`, совпадение описания с
   опубликованным PR по § 5, известные записи о той же ветке или PR.
3. Один подтверждённый каталог переиспользуется целиком; новый каталог для той же
   задачи не создаётся.
4. Отсутствие каталога устанавливается до восстановления или создания: под
   `.agents/local/pr/` нет кандидата, чьё содержимое подтверждает связь с этой
   задачей. Пустой или не относящийся к задаче каталог отсутствием не является,
   пока не исследован.
5. При неясной принадлежности или нескольких несовместимых кандидатах не создавай
   второй источник описания и не перезаписывай ни один из них: остановись и
   сообщи, какие каталоги найдены и чем каждый связан с задачей.

Связанный worktree использует каталог артефактов основной рабочей копии: ему
передаётся корень артефактов задачи, и он не заводит собственный `meta/body.md`.
Если проверка и изменение выполняются в связанном дереве, оно пишет отчёты,
скрипты и рабочие файлы в переданный каталог, а источник описания остаётся в
единственном экземпляре.

Восстановление каталога не создаёт манифест, реестр, базу данных или отдельный CLI:
источником связи служат сами артефакты, метаинформация задачи и фактическое
состояние PR.

### Восстановление источника для уже существующего PR

Локальный игнорируемый файл — рабочий источник, но опубликованный PR нельзя
реконструировать по памяти, постановке задачи или краткому отчёту.

Сначала проверь прежний путь и выполни порядок перехода ниже; не создавай новый
файл из PR поверх несопоставленного локального источника.

Если PR уже существует, а локального источника описания нет либо текущая рабочая
копия ещё не доказала его совпадение с опубликованным описанием:

1. прочитай **полное** текущее описание удалённого PR;
2. создай отсутствующий локальный `.agents/local/pr/<смысловой-идентификатор>/meta/body.md`
   из этого описания без потери существующих разделов, таблиц и текста;
3. перечитай локальный файл и только после этого вноси новое изменение.

Если локальный файл существует, но отличается от удалённого PR, и неизвестно,
какая сторона новее, не перезаписывай ни одну сторону автоматически: сравни их и
явно примири различия. Для уже опубликованного состояния удалённое описание —
основа восстановления, а не повод затереть доказанные локальные изменения.

### Переход со старого пути

При продолжении задачи проверь прежний `body.md` непосредственно в каталоге
задачи. Если он есть, для существующего PR сначала прочитай полное опубликованное
описание. Сравни полное содержимое старого файла, нового файла при его наличии и
PR с нормализацией из § 5. При совпадении перенеси старый файл в `meta/body.md`,
если нового ещё нет; если новый уже существует, сохраняй его, а совпадающий
старый файл можно убрать после проверки. Для ещё не созданного PR перенеси
единственный старый файл без изменения содержимого; если существуют оба файла,
сравни их целиком. При любых несовпадениях или неясном происхождении не затирай
и не удаляй файлы и не меняй PR: сопоставь и
примири различия с пользователем при необходимости. Не мигрируй другие задачи
массово и не создавай постоянный миграционный механизм.

Заголовок, base и head в файле описания не хранятся: сверь их отдельно с аргументами
вызова и фактическим состоянием по § 1.

### Работа без локальной рабочей копии

Если задача явно выполняется **только через GitHub MCP/API**, без доступной
локальной рабочей копии и `gh`, сохрани исходный Markdown во временном рабочем
файле агентской среды (не в Git) и проверь его способом из § 3. Коннектор —
транспорт, а не второй владелец формата и не разрешение обойти проверку описания и
повторное чтение. При публикации через API передавай проверенное полное значение и
обязательно перечитывай опубликованное описание обратно. Если проверку выполнить
невозможно, честно назови это препятствием и не объявляй PR соответствующим
контракту.

## 3. Порядок публикации описания

Для каждого содержательного ручного PR соблюдай один порядок и для нового, и для
существующего PR:

1. Установи репозиторий, base, head и наличие PR; не создавай второй.
2. Подготовь локальное описание. Для существующего PR сначала восстанови его по § 2.
3. Проверь полный файл валидатором из корня репозитория и содержательно — по
   [`pr-body.md`](pr-body.md), § 7 (там же точные команды и собственные тесты
   валидатора).

4. Создай отсутствующий PR либо обнови существующий (§ 4).
5. Прочитай PR обратно (§ 5) и проверь полное описание тем же валидатором.

## 4. Создание и редактирование

Новый PR по умолчанию создаётся **Draft** и остаётся Draft до финального ревью
пользователя, если пользователь не дал другую явную команду или это не следует из
согласованного контракта текущей задачи.

```bash
gh pr create --draft --base <base> --head <branch> --title <title> --body-file <путь>
gh pr edit <number> --title <title> --body-file <путь>
```

Интерфейс `gh` зависит от версии: флаги и способы передать описание проверяй по
выводу `gh pr create --help` / `gh pr edit --help` фактически установленной версии, а
не по памяти. Не полагайся на интерактивные запросы: описание передаётся файлом.

При работе через локальный `gh` описание публикуется только файлом. Встроенный
`--body`, `--body-file -` со stdin и heredoc непосредственно в вызове провайдера
запрещены: они разрывают связь между проверенным локальным файлом и опубликованным
описанием. В режиме GitHub MCP/API без локального `gh` допустима передача
проверенного полного описания через структурированный параметр API с обязательным
повторным чтением, как описано в § 2. Ни тот, ни другой путь не обходит проверку
описания и не отменяет сравнение точного SHA.

## 5. Повторное чтение опубликованного PR

После создания или каждого изменения PR (`gh` либо GitHub MCP/API) перечитай
опубликованный PR и проверь:

```text
репозиторий
base
head
состояние Draft/Ready
заголовок
полное описание
```

Сравни опубликованное описание с локальным файлом с учётом допустимой нормализации
переводов строк (CRLF/CR → LF, завершающий перевод строки). Прочие расхождения
означают, что PR не соответствует локальному источнику, и должны быть устранены,
а не проигнорированы. Повторно прочитанное описание дополнительно прогони тем же
валидатором, что и локальный файл.

Отдельно проверь, что опубликованный head — это именно ожидаемый HEAD текущей
рабочей задачи, а не устаревшее состояние.

Накопительный комментарий CodeRabbit — отдельный объект: его формат, история и
специализированная публикация принадлежат
[`../../coderabbit-review/references/review-report.md`](../../coderabbit-review/references/review-report.md).
Здесь остаётся общая механика PR; чтение и обновление того комментария эта
процедура не заменяет и не дублирует. Исторические таблицы отчёта сохраняются:
новая строка дополняет прежние, а не заменяет их, поскольку накопленная история
остаётся свидетельством предыдущих проверенных ревизий.

При неизвестном результате операции создания или изменения PR сначала выясни
фактическое удалённое состояние и номер PR; не повторяй создание вслепую
([`publication.md`](publication.md), § 7).

## 6. Ready

Draft переводится в Ready только по явной команде пользователя либо когда это
следует из явно определённого контракта текущей рабочей задачи. Успешный push,
зелёный CI или сам факт созданного Draft PR не переводят PR в Ready и тем более
не разрешают merge.

```bash
gh pr ready <number>
```

## 7. Merge

```text
успешный push ≠ разрешение на merge
зелёный CI ≠ разрешение на merge
созданный Draft PR ≠ разрешение на merge
```

Merge выполняется **только** после отдельной текущей явной команды пользователя
на конкретный PR. Разрешение, выданное ранее и относящееся к другому состоянию
рабочей задачи, не переиспользуется.

Перед merge заново проверь:

- репозиторий, base/head и точный текущий HEAD PR (интерфейс установленной версии
  `gh` смотри в `gh pr view --help`);
- актуальность обязательных проверок и ревью относительно **текущего** HEAD:
  после любого изменения HEAD прежние доказательства считаются устаревшими;
- что merge не обходит проверки: `--admin` и любые механизмы принудительного
  слияния запрещены; auto-merge требует того же отдельного разрешения, а ожидающий
  auto-merge **не** считается выполненным merge.

Способ merge выбирай безопасный и согласующийся с фактической политикой
репозитория. Не закрепляй squash жёстко: сверься с фактическим состоянием
репозитория и интерфейсом установленного `gh` (`gh pr merge --help`).

Если установленная версия `gh` умеет привязывать merge к ожидаемому HEAD
(например `--match-head-commit <sha>`), используй эту возможность, чтобы не слить
PR, head которого сдвинулся между проверкой и merge; доступность флага
подтверждается по `gh pr merge --help`.

После merge прочитай фактический конечный статус PR (`merged`) и merge SHA: сам
код завершения команды не подтверждает удалённый результат. Дальше переходи к
уборке (§ 9).

## 8. Продвижение base и конфликты

Если base продвинулась или возник конфликт:

1. Установи общий предок и фактическое изменение обеих сторон (`git merge-base`,
   diff каждой стороны) до любых правок.
2. Разрешай конфликт по смыслу: стратегии целого файла `ours`/`theirs` и общий выбор
   «своей» стороны как механический приём не применяются. Чужие изменения не
   удаляются.
3. Сгенерированный или производный файл, у которого есть владелец-источник,
   пересоздаётся из источника, а не правится вручную.
4. Опубликованная ветка обновляется merge актуальной base, без force и без
   переписывания истории; rebase допустим только для ещё не опубликованной истории.
5. После разрешения проверь отсутствие неслитых путей и незавершённых
   merge/rebase, а также происхождение новой базы и итоговый diff.
6. После изменения HEAD считай прежние результаты CI и ревью устаревшими
   относительно нового коммита и проверь состояние заново: сначала обнови локальный
   файл описания, затем опубликуй и перечитай его (§ 3–5).
7. Не делай force-push опубликованной ветки только ради удобства.

## 9. Уборка после merge

После **подтверждённого** merge допустима обычная уборка собственной рабочей
задачи. Сохраняй `meta/`, отчёты, заметки и полезные скрипты; не удаляй весь
каталог автоматически. Собственные завершённые эксперименты, кэши и рабочие
деревья убирай лишь после сохранения свидетельств и проверки нужного состояния.
Зарегистрированный worktree удаляй штатным `git worktree remove` без принуждения;
неизвестные, грязные или содержащие несохранённые результаты не удаляй. Другие
разрушительные действия требуют соответствующих полномочий.

Удаление удалённой ветки требует выполненного **непосредственно перед удалением**
предусловия:

1. факт слияния конкретного PR подтверждён чтением его состояния (`merged`), а не
   кодом завершения команды merge;
2. установлено состояние рабочей ветки, которое было слито: подтверждённый HEAD
   этой ветки на момент merge (тот, который PR содержал) и соответствующий ему
   удалённый SHA;
3. непосредственно перед удалением прочитан фактический SHA соответствующей
   удалённой ссылки — тем же чтением удалённого состояния, что и в
   [`publication.md`](publication.md), § 6.

Разрешено только одно из двух:

- ссылка уже отсутствует — повторное удаление не требуется, это не ошибка;
- фактический SHA совпадает с подтверждённым состоянием слитого PR — ветка
  удаляется.

Если SHA изменился, принадлежность и сохранность результата не доказаны: **не
удаляй ветку**, оставь её и сообщи причину. Требование равенства SHA рабочего
коммита и merge SHA не выдвигается: при squash-merge и rebase они законно
различаются, поэтому сравнивается состояние рабочей ветки с её собственным
подтверждённым HEAD, а не с merge SHA.

Гонка между чтением ссылки и удалением учитывается: используй удаление с проверкой
ожидаемого состояния, если доступный инструмент это поддерживает и операция
укладывается в действующие полномочия (например `git push --delete` с
`--force-with-lease=<branch>:<ожидаемый-SHA>` для удаления ссылки по ожидаемому
значению). Если поддержки нет, автоматическое удаление небезопасно и не
выполняется: оставь ветку и сообщи ограничение.

Ограничения:

- удаляй ветку только после доказанного сохранения результата: локальную —
  через `git branch -d`, удалённую — только по предусловию выше;
- не удаляй чужую работу и чужие артефакты;
- если squash-merge мешает `git branch -d`, оставь ветку и сообщи ограничение:
  автоматический переход к `-D` и принудительному удалению запрещён;
- уборка не входит в автоматический жизненный цикл: она выполняется после
  подтверждённого merge, а не вместо проверок;
- переписывание опубликованной истории и принудительная локальная уборка
  запрещены и здесь. Это уточнение процедуры не является разрешением выполнять
  реальные операции merge или удаления веток без отдельной команды.

## 10. Завершённое состояние рабочей задачи

```text
коммит опубликован и удалённый SHA подтверждён
PR существует в единственном экземпляре для текущей рабочей ветки
PR перечитан после последнего изменения и соответствует локальному файлу описания
состояние Draft/Ready соответствует ожидаемому
merge не выполнен, пока нет отдельной текущей явной команды
```

До отдельного разрешения на merge конечный результат обычной задачи — проверенный
Draft PR. Результат передаётся пользователю на ревью; merge остаётся за
пользователем.

## 11. Роль CI в проверке описания

Единственный рабочий процесс проверки структуры описания —
`.github/workflows/pr-body.yml`. Он запускается только на событии `pull_request` с
типами `opened`, `edited`, `synchronize`, `reopened`, `ready_for_review`; контекст
проверки — `Структура PR`. Задача CI запускает тесты валидатора, затем сам
валидатор на снимке события `$GITHUB_EVENT_PATH`; отказ любого шага проваливает
задачу.

Что из этого следует читать честно:

- это **кандидатная** проверка кодом из PR, а не независимый доверенный барьер.
  PR, меняющий сам валидатор или рабочий процесс, подлежит содержательному ревью:
  успех такой проверки не доказывает соответствие контракту;
- снимок события — **вход** проверки, а не запрос актуального удалённого описания.
  Изменение описания создаёт новый запуск на `edited`; прежний успешный запуск не
  доказывает проверку новой редакции. Публикация коммита в ветку с открытым PR
  проверяется через `synchronize`; вне PR этот рабочий процесс не запускается;
- новая проверка **не** становится обязательной в настройках защиты ветки без
  отдельного согласованного изменения этих настроек. Обязательность вводится
  после того, как рабочий процесс уже присутствует в основной ветке и подтверждённо
  успешно запускался на подходящем PR: иначе возникает циклическая зависимость,
  где PR требует статус процесса, впервые вводимого этим же PR. Изменение защиты
  ветки — отдельное действие с собственным согласованием, а не побочный эффект
  правки описания или валидатора;
- отсутствие пригодных данных события даёт диагностируемую ошибку, а не обход
  проверки. Сетевой резервный механизм ради получения актуального описания не
  добавляется;
- проверки на штатных событиях PR отражают состояние на момент запуска и не
  гарантируют его неизменность после. После правки описания отдельно прочитай его
  повторно и явно обозначь, если последняя проверка предшествует изменению.

Проверяй фактические настройки защиты ветки и обязательные контексты перед
выводами о них; не выдавай отсутствующий статус за ожидающий запуск и не
ослабляй существующие правила.
