# Описание PR

Этот файл — владелец **содержательной структуры** описания PR. Источник описания,
публикация, повторное чтение, Draft/Ready, merge и очистка принадлежат
[`pr-lifecycle.md`](pr-lifecycle.md); ветка, индекс и коммит — [`publication.md`](publication.md).

## 1. Главный принцип

**Жёсткий предел описания PR — 10 000 кодовых точек Unicode** после нормализации
переводов строк CRLF/CR в LF, включая Markdown. Считаются именно кодовые точки, а
не байты и не «символы» экрана: кириллица отличается от латиницы по байтам, но не
по кодовым точкам.

Внешний Gist, генератор описания и журнал состояния публикации не создаются и не
нужны: все существенные факты находятся в самом PR.

Пиши для человека, который не читал чат и видит только PR. Описание должно быстро
отвечать на вопросы: зачем существует изменение, что именно изменилось, как это
проверено, в каком состоянии CI и какие ограничения остаются.

Заголовок и обычный текст — на русском; точные имена API, командной строки,
файлов, классов, команд, кодов причин и задач CI сохраняются.

Описание строится по **фактическому состоянию** текущей рабочей задачи. Не копируй
исходную постановку, транскрипт агента, полный журнал команд, временный план или
старое состояние, которое уже не соответствует HEAD.

## 2. Обязательная структура

Любой содержательный PR использует настоящие Markdown-заголовки второго уровня.
Обязательных разделов ровно пять, каждый — ровно один видимый заголовок, в таком
относительном порядке:

```text
## Цель
## Изменения
## Проверки
## CI
## Ограничения
```

Дополнительные `##`-разделы разрешены по смыслу и могут стоять между
обязательными; машинной схемы у них нет. Не заменяй структуру одним сплошным
текстом, подписями вида `Проверки:` или единственным списком: разделы отделяются
именно `##`-заголовками.

Заголовок засчитывается только как видимый: каноническая форма `## Название` с
начала строки (допускается отступ до трёх пробелов), необязательные закрывающие `#`
допустимы при корректном синтаксисе. Заголовок не считается, если он находится
внутри HTML-комментария, ограждённого блока кода, блока кода с отступом или
блок-цитаты, — поэтому не прячь разделы в примерах разметки.

### `## Цель`

Причина и ожидаемый результат: какую проблему или возможность закрывает PR, почему
изменение нужно и какое наблюдаемое состояние должно быть после merge. Обычно 1–3
плотных предложения.

### `## Изменения`

Фактическая область и реализация: затронутые подсистемы и типы артефактов, границы
изменения, существенные инженерные решения и их причины, изменённый поток
выполнения или контракт, важную семантику отказа и восстановления после него и
сохранённые инварианты. Пиши о результатах, а не о последовательности действий
агента. Не превращай раздел в
полный список файлов, но и не ограничивайся перечислением путей без смысла.

### `## Проверки`

Только фактически выполненные проверки и их результаты. Для каждой существенной
проверки должно быть понятно, что именно она подтверждает: команда и её результат.
Не выдавай запланированную или недоступную проверку за выполненную — честный статус
«не выполнялось, потому что …» допустим и ожидаем.

### `## CI`

Известное состояние проверок для **конкретного актуального HEAD**: точный HEAD,
если он нужен для исключения устаревших доказательств, обязательные задачи CI и
контексты проверок и их состояние. Если финального результата ещё нет, явно укажи `pending` или
`not run`. Не называй зелёным CI от предыдущего HEAD и не переноси успех старой
редакции описания на новую.

### `## Ограничения`

Только реальные ограничения, риски, недоступные проверки или незавершённое. Если
существенных ограничений нет, скажи это одной строкой («Существенных ограничений
нет») вместо искусственного списка.

## 3. Непустота и заглушки

У каждого обязательного раздела должен быть видимый содержательный текст. Не
считаются содержимым: HTML-комментарии, ограждённые блоки кода, блоки кода с
отступом, пробелы, горизонтальная линия и очевидные заглушки (`TODO`, `TBD`,
`заполнить`, `уточнить`, `…`). Маркер пункта списка сам по себе тоже не является
содержанием: раздел из одних заглушек в маркированном, нумерованном списке или
списке задач отклоняется.

Не требуется минимальное число слов, обязательные цифры или машинно распознаваемый
формат результатов. Осмысленные формулировки вида «Существенных ограничений нет» и
честный статус недоступной проверки принимаются. Проверяется структура и
непустота, а не правдивость содержания: достоверность фактов подтверждает ревьюер,
а не линтер.

## 4. Дополнительные разделы

Добавляй отдельные `##`-разделы, только когда они действительно применимы:

- `## Производительность` — влияние на время выполнения, измеренные сценарии и
  вывод;
- `## Безопасность` — граница доверия, секреты, отдельная проверка безопасности;
- `## Миграция и откат` — совместимость, перенос данных, порядок отката;
- `## Совместимость` — изменение внешнего контракта, ломающие изменения;
- `## Проверка в реальной среде` — ручной прогон, который существенно сильнее
  статических проверок: сценарий, наблюдаемый результат, уборка временных данных.

Эти разделы необязательны и не имеют отдельной машинной схемы. Если фактов нет —
не создавай пустой раздел ради вида.

Накопительный отчёт CodeRabbit живёт в отдельном комментарии PR, а **не** в
описании: его формат, история и публикация принадлежат
[`../../coderabbit-review/references/review-report.md`](../../coderabbit-review/references/review-report.md).
Пять обязательных разделов выше от этого не меняются, и отчёт в них не
переносится.

## 5. Плотность и читаемость

Обычно достаточно короткого абзаца или 2–6 содержательных пунктов на раздел. Это
ориентир, а не квота. Для крупной работы раздел может быть длиннее, но сплошной
текст разбивай по смыслу.

Предпочитай короткие абзацы, списки для независимых фактов, таблицы только для
действительно табличных данных и строчный код для путей, команд, SHA и
идентификаторов. Не повторяй одно и то же доказательство в нескольких разделах.

## 6. Локальный источник описания

Владелец этого контракта — [`pr-lifecycle.md`](pr-lifecycle.md), § 2: путь
`.agents/local/pr/<смысловой-идентификатор>/meta/body.md`, правило игнорирования Git и
проверка отсутствия файла в индексе описаны там и не дублируются здесь.

Здесь остаются только требования к содержанию: файл формируется и
перечитывается целиком до публикации, его структура проверяется по § 2–3, а
шаблонизатор, генератор или схема описания не вводятся.

## 7. Проверка описания перед публикацией

Перед созданием и перед каждым изменением PR проверь полный Markdown-файл
локальным валидатором из корня репозитория (Go-модуля в репозитории нет):

```bash
go run .github/scripts/pr-body-lint/main.go --body-file "$body_file"
```

Тот же механизм проверяет снимок события GitHub:

```bash
go run .github/scripts/pr-body-lint/main.go --event-file "$GITHUB_EVENT_PATH"
```

Собственные тесты валидатора:

```bash
go test .github/scripts/pr-body-lint/main.go .github/scripts/pr-body-lint/main_test.go
```

Валидатор не делает HTTP-запросов, не читает токены, не проверяет фактические
CI-статусы и не анализирует содержание комментариев: он проверяет форму описания.

## 8. Актуализация описания

Описание — живое описание PR, а не текст только на момент создания.

При изменении фактов:

1. сначала обнови локальный `.agents/local/pr/<смысловой-идентификатор>/meta/body.md`;
2. перечитай полный файл и проверь его структуру валидатором (§ 7);
3. опубликуй его способом из [`pr-lifecycle.md`](pr-lifecycle.md);
4. перечитай опубликованный PR и проверь его полное описание тем же валидатором,
   сопоставив с локальным источником.

Правка описания сама по себе создаёт новый запуск проверки на событии `edited`:
не устраивай цикл «запуск → правка строки CI → запуск». Указывай конкретный HEAD или
явно отмечай, что актуального результата для новой редакции ещё нет.
