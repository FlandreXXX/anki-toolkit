# Публикация: ветка, индекс, commit, push, удалённое состояние

Этот файл владеет порядком действий обычной публикуемой задачи до
подтверждённого удалённого состояния. Контракт и границы задаёт `SKILL.md`.

## 1. Установить фактическое состояние рабочей копии

Перед изменением состояния зафиксируй идентичность репозитория и текущее
состояние:

```bash
git rev-parse --show-toplevel
git remote -v
git rev-parse --abbrev-ref HEAD
git status --porcelain
git rev-parse HEAD
```

Прежде чем публиковать, обнови удалённые ссылки, а не доверяй кэшу
удалённых ссылок слежения:

```bash
git fetch <remote> --prune
```

Препятствием публикации являются два разных состояния, и путать их нельзя:

- **неразрешимая неоднозначность назначения** — рабочая копия не относится к
  ожидаемому репозиторию, не удаётся однозначно установить целевую ссылку
  публикации либо у существующей рабочей задачи потеряна или противоречива
  ожидаемая связь ветки с удалённым репозиторием. Это состояние, требующее
  решения: не угадывай, не переключай ветки молча и не назначай удалённый
  репозиторий произвольно;
- **штатное отсутствие upstream** у ещё не опубликованной рабочей ветки. Это не
  препятствие: имя ветки известно из текущей рабочей копии, а целевой удалённый
  репозиторий определяется по фактическому состоянию (см. § 2), после чего первая
  публикация выполняется с `--set-upstream` (см. § 5).

Отсутствие upstream само по себе не блокирует работу и не является основанием
остановиться до выполнения процедуры.

## 2. Ветка

### Новая самостоятельная задача

1. Установи фактический удалённый репозиторий, а не предполагай `origin` по
   умолчанию: возьми его из upstream текущей ветки, а если upstream ещё нет — из
   фактического состояния `git remote -v`. Целевой репозиторий и целевая ссылка
   обязаны быть установлены однозначно из фактического состояния; если
   единственного кандидата нет — это неразрешимая неоднозначность (§ 1), а не
   повод выбрать один из них наугад.
2. Установи ветку по умолчанию и базовую ветку из **удалённого** состояния, а не
   по памяти:

   ```bash
   git ls-remote --symref <remote> HEAD
   ```

   Локальная ссылка `refs/remotes/<remote>/HEAD` кэшируется и может быть
   устаревшей, поэтому источником истины не является.
3. Обнови базу безопасно (fetch; при необходимости fast-forward локальной базы).
4. Создай смысловую рабочую ветку от этой базы. Имя отражает область и содержание
   задачи; временные идентификаторы этапов плана в имя ветки не попадают.
5. Не подмешивай неизвестные пользовательские изменения.

### Продолжение существующей задачи

Используй существующую ветку, а не новую. Перед продолжением проверь её
идентичность, upstream и связанный PR по
[`pr-lifecycle.md`](pr-lifecycle.md), § «Идентичность PR». Новая ветка не
создаётся только потому, что началась следующая фаза той же рабочей задачи.

### Прямая работа в ветке по умолчанию

Работа в ветке по умолчанию напрямую не ведётся: это постоянное правило
репозитория (`AGENTS.md`, раздел «Git и публикация»).

Явная просьба работать прямо в ветке по умолчанию конфликтует с этим правилом. Это
не исключение и не переопределение инварианта на будущее, а состояние, требующее
решения: сообщи конфликт и предложи рабочую ветку, а не начинай молча писать в
ветку по умолчанию.

## 3. Проверки и подготовка индекса

1. Выполни применимые проверки от их фактических владельцев (`AGENTS.md`,
   документация затронутой области, CI репозитория). Скилл не подменяет набор
   проверок и не решает, какие проверки нужны.
2. Просмотри итоговый diff целиком, а не только список файлов.
3. Подготовь индекс только по путям текущей рабочей задачи:

   ```bash
   git add -- <путь> [<путь> ...]
   ```

4. Перечитай подготовленный diff и убедись, что в индекс попало ровно ожидаемое:

   ```bash
   git diff --cached --stat
   git diff --cached
   git status --porcelain
   ```

Случайные подготовленные и неотслеживаемые файлы пользователя не захватываются:
их не добавляют, не коммитят и не удаляют. В индекс не попадают локальные
артефакты `.agents/local/` и чужая подготовка индекса. Если принадлежность
изменений установить нельзя — это состояние, требующее решения, а не повод
угадывать.

## 4. Commit

- Сообщение на русском языке и описывает фактическое изменение, а не исходный
  замысел.
- Если в репозитории есть устойчивый стиль сообщений, сохраняй его.
- В сообщение не попадают номер текущего PR, SHA, имя этапа и разовый план.
- Коммит делается в текущей ветке текущей рабочей задачи; несвязанные локальные
  изменения в него не попадают.
- Коммит сам по себе не завершает публикуемую задачу (`SKILL.md`).

Пустой коммит допустим только там, где это требует отдельно определённый порядок
работы репозитория, а не как способ закрыть задачу без изменений.

Узкое разрешение этого репозитория: `git commit --allow-empty` допустим как
маркер **подтверждённой завершённой итерации** цикла CodeRabbit, в которой ревью
прошло полностью и необходимых исправлений нет. Условия завершённости итерации и
содержание такого сообщения задаёт специализированный контракт:
[`../../coderabbit-review/SKILL.md`](../../coderabbit-review/SKILL.md),
[`../../coderabbit-review/references/review-report.md`](../../coderabbit-review/references/review-report.md).
На обычные задачи это разрешение не распространяется: пустой коммит там остаётся
недопустимым.

## 5. Push

Публикуй текущую рабочую ветку **явно** в ожидаемый удалённый репозиторий и
ссылку.

Перед push прочитай удалённую ссылку и сравни её с локальным состоянием: так
обнаруживаются невидимые локально удалённые коммиты, и публикация не превращается
в неожиданный отказ. Голый `git push` не является контрактом скилла: он
подчиняется `push.default` и другим настройкам Git и в конфигурациях вида
`matching` может опубликовать несколько ссылок.

Если удалённая ссылка расходится с локальным состоянием, порядок такой:

1. получи удалённые коммиты и изучи их до любых действий: `git fetch <remote>`,
   затем граф (`git log --graph --oneline <remote>/<branch>`) и фактическое
   изменение относительно общего предка (`git merge-base`, `git diff`);
2. определи, что это за состояние. Чужие коммиты не перезаписываются. Расхождение,
   которое нельзя свести обычным путём текущей рабочей задачи, — это препятствие:
   остановись, назови конкретную причину и последний подтверждённый опубликованный
   HEAD. Не расширяй задачу молча до разрешения чужой истории;
3. force-push и переписывание истории для «разрешения» расхождения запрещены
   (см. § 8) и основанием для них расхождение не является.

Отказ обычного push без force при non-fast-forward — это более поздний барьер, а не
замена чтению удалённого состояния. Проверяй ссылку непосредственно перед push и
не продолжай push, если ссылка изменилась между проверкой и push.

```bash
git ls-remote --refs <remote> refs/heads/<branch>

# первая публикация ветки: новый upstream
git push --set-upstream <remote> refs/heads/<branch>:refs/heads/<branch>

# последующая публикация: явный удалённый репозиторий и refspec
git push <remote> refs/heads/<branch>:refs/heads/<branch>
```

Первая публикация рабочей ветки, у которой ещё нет upstream, — штатное состояние,
а не препятствие. Для неё обязательны два условия, установленные **из фактического
состояния**, а не по соглашению:

- целевой удалённый репозиторий определён однозначно (§ 1–2);
- целевая ссылка `refs/heads/<branch>` определена однозначно из текущей рабочей
  копии и ещё не содержит чужих коммитов этой задачи (`git ls-remote` выше).

`<remote>` выбирается по процедуре § 1–2: из upstream ветки, если он есть, иначе из
фактического состояния `git remote -v`; произвольно он не назначается. Если
единственного удалённого репозитория или ссылки установить нельзя, публикация не
выполняется: это неразрешимая неоднозначность назначения (§ 1). Push выполняется
без force: force-push требует отдельного явного основания (см. § 8).

## 6. Удалённое постусловие

Публикация подтверждена только тогда, когда выполнено:

```text
ожидаемый локальный HEAD == фактический SHA соответствующей удалённой ветки
```

Ссылка слежения за удалённой ветвью (`refs/remotes/...`) для этого не годится: она
может быть устаревшей. Читай саму удалённую ссылку:

```bash
git rev-parse HEAD
git ls-remote --refs <remote> refs/heads/<branch>
```

Сравни полученные SHA по точному значению. Совпадение — единственное
доказательство доставки. Расхождение означает, что ожидаемое изменение не
опубликовано, и работа не завершена.

`git ls-remote --refs` здесь предпочтителен, потому что отдаёт только ссылки, без
`^{}`-строк разыменованных аннотаций, и даёт однозначное сравнение. Если фактическая
среда требует другого нативного механизма, используй эквивалент, который читает
именно удалённую ссылку, и назови его явно.

## 7. Протокол неизвестного результата сетевой операции

Если push (или любое другое сетевое изменение) завершился неизвестным результатом —
таймаут, обрыв соединения, неясный ответ, — порядок строго такой:

1. Сначала установи фактическое удалённое состояние **чтением**:
   `git ls-remote --refs <remote> refs/heads/<branch>`.
2. Не повторяй push вслепую.
3. Повторяй изменение только тогда, когда доказано, что ожидаемое изменение не
   было доставлено.
4. Не перезаписывай чужие новые удалённые коммиты.

То же правило действует для создания и редактирования PR: неизвестный результат
сначала разрешается чтением удалённого состояния PR, и только потом изменение
повторяется — если доказано, что оно не применилось. Появление второго PR для
того же репозитория/base/head — дефект, а не допустимый исход гонки.

Постоянный журнал публикации или автомат состояний для этого не нужны: достаточно
чтения фактического удалённого состояния.

## 8. Запрещено без отдельного обоснованного разрешения в текущем запросе

- force-push;
- переписывание опубликованной истории (rebase/amend уже опубликованных
  коммитов);
- удаление неизвестных удалённых ветвей;
- публикация другой ветки вместо текущей рабочей задачи;
- публикация несвязанных локальных изменений;
- смена base PR, переключение на другой PR и закрытие PR.

## 9. Выполнение через GitHub MCP без локальной рабочей копии

Когда пользователь поручил GitHub-операции через коннектор и локальная рабочая
копия недоступна, используй структурированный GitHub API. Установи фактический
base commit/ref из удалённого состояния, создай рабочую ветку от точного SHA,
подготовь Git tree с **явно перечисленными** изменёнными файлами, создай коммит с
этим родителем и опубликуй его обычным fast-forward обновлением **только** ссылки
рабочей ветки. После обновления заново прочитай удалённую ссылку и сравни её точный
SHA с коммитом. Перед созданием PR проверь реальный diff этой ветки. Если удалённая
ссылка не совпадает с ожидаемой или результат изменения неизвестен, сначала
перечитай состояние; никогда не перезаписывай чужие изменения.

Этот путь не обходит проверку описания по
[`pr-body.md`](pr-body.md) и не отменяет сравнение точного SHA, повторное чтение
опубликованного PR и запрет на merge без отдельной команды: коннектор — транспорт,
а не второй владелец процедуры.

## 10. Завершённое состояние публикации

Шаг публикации завершён, когда:

```text
подготовленный diff соответствует задаче
коммит создан в рабочей ветке текущей задачи
push выполнен явно в ожидаемый удалённый репозиторий и ссылку
фактический SHA удалённой ветки равен ожидаемому локальному HEAD
```

Только после этого переходи к жизненному циклу PR
([`pr-lifecycle.md`](pr-lifecycle.md)) и к передаче результата пользователю.
