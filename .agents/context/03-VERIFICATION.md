# Проверки: команды, границы, доказательность

Фактические команды этого репозитория и то, что каждая из них доказывает.
Значения, полученные в чужом окружении, не переносятся: команда выполняется заново
на текущей редакции изменений.

## Общее правило

Go-модуля в репозитории нет, поэтому `go vet` и `go test` не работают в режиме
каталога (`.`, `./...`, путь к пакету) — они требуют модуль. Обе утилиты
запускаются и тестируются **именованными файлами** из корня репозитория. Команды
ниже проверены в этой форме; другая форма — не «почти то же самое», а отказ.

`gofmt` работает и с каталогом: он не требует модуля.

## `pr-body-lint`

Проверка описания PR по локальному файлу и по снимку события:

```bash
go run .github/scripts/pr-body-lint/main.go --body-file "$body_file"
go run .github/scripts/pr-body-lint/main.go --event-file "$GITHUB_EVENT_PATH"
```

Собственные тесты утилиты:

```bash
go test -count=1 .github/scripts/pr-body-lint/main.go .github/scripts/pr-body-lint/main_test.go
```

Коды выхода: `0` — структура соответствует контракту (в режиме события — включая
узкое исключение ботов), `1` — нарушение контракта, `2` — ошибка использования или
входа.

Что проверяется: наличие пяти обязательных разделов в установленном порядке и
видимого содержательного текста в каждом, предел 10 000 кодовых точек Unicode.
Проверяется структура, а не правдивость содержания. Сеть, токены и CI-статусы
утилита не читает.

## `coderabbit-comment-lint`

Два взаимоисключающих режима — чистая проверка формы отчёта и сверка
опубликованного состояния только на чтение:

```bash
go run .github/scripts/coderabbit-comment-lint/main.go --comment-file "$comment_file"
go run .github/scripts/coderabbit-comment-lint/main.go --event-file "$GITHUB_EVENT_PATH"
```

Собственные тесты утилиты:

```bash
go test -count=1 .github/scripts/coderabbit-comment-lint/main.go .github/scripts/coderabbit-comment-lint/main_test.go
```

Коды выхода: `0` — соответствует, `1` — нарушение контракта, `2` — ошибка
использования или входа либо невозможность достоверной проверки.

Режим устанавливается фактом передачи флага, а не значением пути: пустое значение
или одновременная передача обоих флагов — ошибка использования (`2`) до чтения
файла и сети.

`--comment-file` — только форма: служебный маркер и накопительная таблица,
видимость Markdown, последовательность итераций и история. Удалённое авторство и
сеть не затрагиваются. Структура таблицы разбирается по исходной строке, поэтому
HTML-комментарий внутри строки отчёта не меняет число ячеек. `--event-file` — сеть
только на чтение: идентичность PR с событием и с `GITHUB_REPOSITORY`, фактический
автор, полная постраничная выдача комментариев верхнего уровня, повторное чтение
PR. Каноническая ссылка пагинации принимается только при точном совпадении
числового идентификатора репозитория назначения (`base.repo.id` из ответа API о
PR). Структуру описания PR этот режим не проверяет — это отдельная утилита.

## Общие проверки Go

Форматирование — по каталогам или по именованным файлам:

```bash
gofmt -l .github/scripts
gofmt -l .github/scripts/pr-body-lint/main.go .github/scripts/pr-body-lint/main_test.go
```

Пустой вывод означает соответствие; перечисленные файлы — те, что нужно
отформатировать.

Статический разбор — именованными файлами:

```bash
go vet .github/scripts/pr-body-lint/main.go .github/scripts/pr-body-lint/main_test.go
go vet .github/scripts/coderabbit-comment-lint/main.go .github/scripts/coderabbit-comment-lint/main_test.go
```

Тесты — именованными файлами; `-count=1` обязателен локально, иначе результат
может быть взят из кэша тестов и не относиться к текущей редакции:

```bash
go test -count=1 .github/scripts/pr-body-lint/main.go .github/scripts/pr-body-lint/main_test.go
go test -count=1 .github/scripts/coderabbit-comment-lint/main.go .github/scripts/coderabbit-comment-lint/main_test.go

go test -count=1 -race .github/scripts/pr-body-lint/main.go .github/scripts/pr-body-lint/main_test.go
go test -count=1 -race .github/scripts/coderabbit-comment-lint/main.go .github/scripts/coderabbit-comment-lint/main_test.go
```

`-race` выполняется при доступности race detector в текущем окружении;
недоступность `-race` — честно названное ограничение, а не пройденная проверка.

CI запускает те же тесты без `-count=1` — ровно в такой форме:

```bash
go test .github/scripts/pr-body-lint/main.go .github/scripts/pr-body-lint/main_test.go
go test .github/scripts/coderabbit-comment-lint/main.go .github/scripts/coderabbit-comment-lint/main_test.go
```

Тесты утилит не обращаются к реальному GitHub API и к CodeRabbit: сетевой транспорт
подменяется в тестах, входы синтетические.

## Границы проверок

- **Локальные и чистые** — `gofmt`, `go vet`, `go test`, `--body-file`,
  `--comment-file`. Сети не требуют, результат детерминирован, ограничен формой
  входа.
- **Сетевые** — только `--event-file` у `coderabbit-comment-lint`. Нужны
  `GITHUB_REPOSITORY` и `GITHUB_TOKEN` в окружении шага; выполняются только GET к
  документированному GitHub API. Проверяют **прочитанное** состояние, а не
  атомарный снимок: между чтениями удалённое состояние может измениться, и
  расхождение означает неподтверждённую проверку, а не успех.
- **Метаданные и ссылки** — относительные ссылки в документации и метаданные
  скиллов не проверяются ни одной утилитой этого репозитория: отдельного
  линтера Markdown-ссылок здесь нет. Ссылки, на которые опирается задача,
  проверяются разрешением фактических целей в рабочей копии.

## `.coderabbit.yaml`

Конфигурация провайдера по схеме V3: `version: 3`. Проверяется официальной JSON
Schema, а не CLI:

```bash
check-jsonschema --no-cache --schemafile https://www.coderabbit.ai/integrations/schema.v3.json .coderabbit.yaml
```

`0` — файл соответствует схеме; `1` — нарушение: в V3 неизвестные поля и опечатки
отвергаются, включая вложенные объекты. Проверка требует установленного
`check-jsonschema` и доступа к URL схемы; ненулевой код не доказывает сам по себе
невалидность — различай ошибку файла, отсутствие инструмента и сетевую ошибку по
выводу команды.

`coderabbit config validate` для этого не используется: `coderabbit config` без
подкоманды запускает guided setup и может записать файл, а `config apply`
применяет предложение. Схема V3 — opt-in для GitHub Cloud; локальный CLI её не
применяет, и настоящий эффект виден только в hosted-ревью. Синтаксическая
валидность не доказывает, что hosted-ревью действительно запустится.

## CI: job `Структура PR`

Единственный рабочий процесс — [`.github/workflows/pr-body.yml`](../../.github/workflows/pr-body.yml).
Он запускается только на событии `pull_request` с типами `opened`, `edited`,
`synchronize`, `reopened`, `ready_for_review`; контекст проверки — `Структура PR`.
Шаги: тесты `pr-body-lint`, проверка описания из снимка события, тесты
`coderabbit-comment-lint`, проверка опубликованного отчёта только на чтение. Отказ
любого шага проваливает job.

Что job доказывает: тесты и утилиты из кода PR выполняются и завершаются успешно
на снимке события этого запуска, а опубликованное на момент сетевого шага
состояние PR и его комментариев соответствует контракту отчёта.

Чего он **не** доказывает:

- это проверка кодом самой проверяемой ревизии PR, а не независимый доверенный
  барьер: PR, меняющий утилиты или рабочий процесс, требует содержательного ревью,
  и его зелёный статус не доказывает соответствие контракту;
- снимок события — вход проверки, а не запрос актуального описания; успешный
  запуск не переносится на более позднюю редакцию описания или другой HEAD;
- сетевая проверка относится к прочитанному состоянию: она не является атомарным
  снимком комментариев и не гарантирует их неизменность после запуска;
- отсутствие отчёта CodeRabbit — допустимое состояние, а не доказательство того,
  что ревью проводилось;
- job не доказывает независимость валидаторов от кода PR, не проверяет
  правдивость содержания описания и не заменяет содержательное ревью.

Публикация комментария или изменение комментария не запускает `pull_request`:
после публикации отчёта проверка выполняется отдельно, независимо от CI.

## `actionlint`

`actionlint` может проверять рабочий процесс; наличие инструмента и его версию
устанавливай фактом в текущей среде, а не по этому документу:

```bash
command -v actionlint && actionlint --version
actionlint .github/workflows/pr-body.yml
```

Это **локальная** проверка синтаксиса и структуры рабочего процесса. В CI репозитория
`actionlint` **не запускается**, поэтому зелёный job не доказывает его прохождение,
а успешный локальный прогон не является статусом CI. Изменения
`.github/workflows/pr-body.yml` дополнительно сверяются структурно: события,
шаги, разрешения и передача токена только в окружение сетевого шага.

## Правило доказательности

- Недоступную проверку называй недоступной, а не пройденной.
- Прошлый успех не переносится на новую редакцию изменений или другой HEAD.
- Команда указывается точная, вместе с результатом; «должно работать» не является
  результатом.
- Проверка формы не доказывает правдивость содержания, а прохождение линтера — что
  ревью, коммиты и находки действительно существуют.
